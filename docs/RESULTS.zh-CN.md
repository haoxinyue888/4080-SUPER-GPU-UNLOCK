# 实测结果与结论边界

本研究基于**一张运行 Windows 11 的耕升 RTX 4080 SUPER（AD103，16 GB）**。数据可以证明该系统在特定会话中的 **FP16/BF16 稠密 GEMM 计算吞吐量**变化，但不能证明存在适用于所有 RTX 4080 SUPER 的通用解锁方案。

## 已保存的测量结果

下表全部为 **8192 × 8192 × 8192 矩阵乘法**的有效吞吐量，单位为 **TFLOPS**。

| 观测情况 | FP16 | BF16 | 说明 |
|---|---:|---:|---|
| 原始未解锁基线 | **101.303** | **101.398** | 成功实验前的基线 |
| 第二组接近未解锁的数据 | 104.870 | 104.907 | 早期一次实验未成功、实体关机后的测量 |
| 成功解锁的 Windows 会话 — A | **171.552（+69.3%）** | **174.711（+72.3%）** | RUN02 会话保存的第一组数据 |
| 成功解锁的 Windows 会话 — B | **168.488（+66.3%）** | **170.911（+68.6%）** | 同一 RUN02 会话内的独立重复测量 |
| 未使用 USB 解锁流程的普通重启 | 102.698 | 98.965 | 吞吐量恢复到接近未解锁水平 |
| 后续成功交接（与 RUN05 相关） | **163.409（+61.3%）** | **169.331（+67.0%）** | 另一组已保存的交接后性能测量 |

所有百分比均以**最初那组**对应精度的未解锁数据为基线计算。

**关于 RUN06：** USB 优先启动、GPU 恢复和 Windows 交接的成功，有启动前日志以及使用者确认的 Windows 启动作为证据。但**没有单独标记为 RUN06 的 GEMM 测量结果**，因此不能将 RUN05 的数据归入 RUN06。

## 基准测试方法

- **运算：** 在 CUDA 上使用 PyTorch `torch.mm`，对已驻留在 GPU 显存中的 FP16 或 BF16 矩阵进行乘法。
- **规模：** 8192³，输出缓冲区提前分配。
- **预热：** 12 次矩阵乘法。
- **计时：** 每种精度各进行 5 组、每组 15 次乘法；采用计时组的中位数。
- **有效计算吞吐量：** 按 `2 × N³ / elapsed_seconds` 计算并以 TFLOPS 表示。
- **TF32：** 已禁用。
- 未解锁和解锁后的测试保留了相同的核心矩阵运算及计时方法。

这种方法主要测量 **GPU 内部的稠密矩阵计算能力**，**不等于**游戏帧率、模型推理吞吐量、显存容量、显示功能或应用整体速度的提升。

## 现有证据能够支持什么

**已经观察到：**

- 在这一张特定显卡上，经人工确认的启动前实验成功交接到 Windows。
- RUN02 会话内的两次测量，相对于最初基线显示约 **66–72% 的 FP16/BF16 GEMM 吞吐量提升**。
- 后续与 RUN05 相关的独立保存数据也显示吞吐量提高。
- 一次**未重复 USB 解锁操作**的普通 Windows 重启，使计算性能恢复到接近基线水平。
- RUN06 验证的是首次扫描启动与交接流程，**并不是新的性能基准数据**。

**尚未确立：**

- 对其他 RTX 4080 SUPER 板卡及 VBIOS 版本的兼容性。
- 每次重启或每一种初始硬件状态都能成功解锁。
- 长时间负载稳定性、完整的数值计算正确性，以及不存在硬件风险。
- 游戏 FPS、LLM token/s 等实际应用性能提升。
- 后续冷启动、休眠唤醒、驱动变化或其他生命周期事件中的效果保留情况。

本仓库刻意**不公开原始 JSON、硬件日志及 ROM/PROM 数据**。上表仅整理经过核对的测量数值，不包含私人主机元数据。
