# 我们为耕升 RTX 4080 SUPER 做了哪些适配

这是一份**针对具体显卡的独立案例研究**，并非一种全新的 GPU 解锁技术。技术基础来自早期 GPU 解锁研究，以及 TOTORONG 针对**改装为 32 GB 的非 SUPER 版 RTX 4080** 所记录的 Windows UEFI 实现。参见[上游致谢](../REFERENCES.zh-CN.md)。

我们的实测对象是**一张耕升（Gainward）RTX 4080 SUPER（AD103，16 GB）**，同时承担显示输出和 CUDA 计算任务。其他厂商的 RTX 4080 SUPER，甚至同一产品的不同硬件修订，都必须独立验证。

## 上游方案与我们的适配工作

| 领域 | 上游已有的内容 | 我们针对耕升显卡完成的工作 |
|---|---|---|
| 计算性能解锁 | 底层 GPU 固件解锁思路 | 通过只读检查及真实硬件实验，验证其在这张显卡上的适用性 |
| Windows UEFI 流程 | 预加载 Windows、人工确认、图形恢复及 Windows 交接 | 调整显卡预检查、图形设备所有权验证和 Windows 交接检查 |
| 硬件配置 | 以原参考显卡为基础的假设 | 核实实际 **16 GB** 显存布局、GPU 身份及 ROM/PROM 证据 |
| 图形驱动所有权 | 单 GPU 的 UEFI 驱动释放流程 | 正确处理我们主板上经验证的额外 UEFI 图形子控制器 |
| 初始状态验证 | 基于参考显卡的启动状态 | 调查不同的冷启动读数，采用有明确边界且会重新检查的验证方式 |
| 启动管理器查找 | 预加载 Windows 启动程序 | 针对 USB 优先启动时首次找不到 Windows 的问题，加入有次数限制的查找重试 |
| 故障诊断 | 原有状态日志机制 | 利用持久化、逐次编号的报告及最终阶段记录定位具体故障 |

以上任何一项都**不代表修改后对所有显卡安全**。**不要把其他显卡的身份值、校验值、寄存器数值或 EFI 文件直接复制到自己的硬件上。**

## 真实硬件实验历程

| 实验 | 实际发生的情况 | 得到的教训 |
|---|---|---|
| **RUN00** | 初始检查发现第二个未预期的 UEFI 图形驱动子控制器，因此拒绝继续。**没有启动解锁操作。** | 合法的设备所有权结构可能比参考程序预期的更复杂；应核实真实驱动与设备的关系，而不是跳过验证。 |
| **RUN01** | 实验固件步骤与图形重新连接已推进，但重新连接后的 PCI 命令寄存器检查过于严格，导致 Windows 交接被拒绝，程序停止。 | UEFI 图形驱动重新接管设备时，可能合理地改变某一限定状态；我们需要的是经过测试的精确例外，而不是全面放宽检查。 |
| **RUN02** | 修正后的实验程序完成恢复并进入 Windows。同一会话内的两次 FP16/BF16 测试显示显著提升。 | 固件读回成功本身不等于计算加速成功；必须在 Windows 中独立测量。 |
| **RUN03** | 普通重启后，GPU 初始选择器读数与上次成功启动不同。预检查在**修改 GPU 之前就拒绝继续**。 | 先前测到的初始值不能被当成所有情况下都成立的条件。之后的有界适配通过了模拟测试，但不能证明所有初始状态都安全。 |
| **RUN04** | USB 优先启动时，Windows 预加载阶段找不到 Windows Boot Manager，**未启动 GPU 解锁操作**。 | 在释放唯一显示 GPU 的 UEFI 驱动前，必须确认 Windows 启动程序可用。 |
| **RUN05** | 返回固件并再次启动程序后，成功找到 Windows；经人工确认的实验进入 Windows。保存的性能测试显示吞吐量提升。 | 第二次启动成功说明存在真实的启动路径兼容性问题，但不能单凭这一现象确定其根本原因。 |
| **RUN06** | 改进后的程序在**首次扫描**就找到 Windows 启动程序，完成经人工确认的操作、恢复图形并成功交接。 | 首次扫描的正常路径已在真实硬件上验证；额外的延迟查找和存储驱动连接回退机制**仅通过模拟测试**，RUN06 并未触发它们。 |

有界 Windows 查找改进通过了 **69/69 个主机模拟场景**。这属于软件模拟证据，不代表所有主板的 UEFI 存储驱动行为都相同。

## 结果最依赖哪些原则

1. **先有证据，再做适配。** 在修改假设前确认具体显卡、显存布局、固件身份和只读初始状态。
2. **检查不通过就停止（fail-closed）。** 设备所有权异常、固件不匹配、找不到 Windows 启动程序或无法确认安全清理，都应阻止实验继续。
3. **记录每次关键判断。** 日志区分 `attempted=0` 的预检查拒绝和真正发生过的硬件操作。
4. **有序交接。** 在确认 GPU、图形功能恢复及 Windows 交接之前，不把操作判定为完整成功。
5. **Windows 内独立测试。** 成功启动后的性能测量，与后续重启是否保留效果，必须分开记录。

**范围说明：** 本研究只关注解锁实现及直接观察到的计算性能变化，不是通用 PC 调优、驱动更新或主板维护指南。
